Dynamically optimize shuffle write parallelism 
                                                                 Authors: Erik Fang, Yanze Jiang
Abstract
In current Celeborn implementation, each partition is described as a series of PartitionLocation with sequential epoch ids. For each partition, only one partitionLocation, known as the latestPartitionLocation, is actively for writes at any time. Since each PartitionLocation corresponds to a file on worker, partition write performance is constrained by the I/O capacity of a single worker, potentially creating a bottleneck in data throughput.


While this architecture generally performs well, it can lead to significant performance degradation in specific scenarios:
* partition skew
    If certain partitions are significantly larger than others, they may take considerably longer to write, eventually slowing down the entire job. In real-world cases, we have observed that skewed partitions with high write speeds can quickly reach the soft split threshold and get promoted to a hard split within seconds. This event forces all Spark MapTasks to pause and await a new partition location via revive RPC calls, which substantially increases the total shuffle write time.
* small partition number
    Shuffle write parallelism is controlled by the compute framework, such as Spark or Flink, and may be set to a low value for scenarios like single partition. As a result, when shuffle write parallelism is tied directly to partition number, it can lead to suboptimal performance.


    To mitigate these limitations, this document proposes an enhancement that enables concurrent writes to multiple PartitionLocations for a single partition. Furthermore, the system will dynamically detect and adjust shuffle write parallelism based on real-time feedback from shuffle client.
Goal
The primary objectives of this proposal are:
* To enable shuffle client to write to one single partition with multiple PartitionLocations in parallel
* to improve LifecycleManager to dynamically detect and optimize write parallelism for each partition, based on the observed frequency of partition splits. 
Design
Shuffle Client Modifications
In ShuffleClientImpl, the previous 1:1 mapping between partitionId and PartitionLocation is updated to a 1:N mapping managed by LocationManager. This change allowes data for a single partition to be splitted and written to multiple locations concurrently. For simplicity, mapId will be hashed to select the target PartitionLocation from the available set in LocationManager.
With multiple candidate PartitionLocations now available, occasional unavailability—due to push failures or hard splits—no longer stalls shuffle write. ShuffleClient can seamlessly switch to alternative PartitionLocations to contine writing while reporting the unavailable ones to the LifecycleManager via a non-urgent reviveRequest[a][b][c]. Only when all available PartitionLocations become unusable, ShuffleClient sends an urgent reviveRequest to LifecycleManager, indicating it is blocked and requires a new PartitionLocation to proceed.
Lifecycle Manager Enhancements
Within LifecycleManager, a PartitionLocationMonitor is introduced to dynamically determine the appropriate write parallelism for each shuffle partition. By default, each partition starts with a parallelism of 1. As the PartitionLocationMonitor receives notifications of SOFT_SPLIT (triggered after writing 1GB by default) and HARD_SPLIT (triggered after writing 3GB by default), it estimates the data push speed for each partition based on the frequency of these splits. 
Assuming that each worker has an I/O bandwidth limit that affects flush performance, the optimal partition write parallel level is calculated as follows:


Partition Write Parallelism = Push Speed / Expected Worker Flush Speed[d][e]


This adaptive approach ensures that partitions with higher write loads can scale their parallelism accordingly, decoupling write performance from the statically configured partition number.
Refining HARD_SPLIT Semantics
In current PushDataHandler, a HARD_SPLIT response can be triggered by four distinct conditions:
1. The PartitionLocation size exceeds WORKER_PARTITION_SPLIT_MAX_SIZE
2. The worker enters shutdown status due to Graceful Shutdown or Decommission
3. The worker's actualUsableSpace is less than the WORKER_DISK_RESERVE_SIZE
, indicating that the worker's disk is full.
4. The PartitionLocation has already been committed.


It is proposed that these conditions be disaggregated by introducing more specific StatusCode[f][g][h][i][j], such as WORKER_SHUTDOWN,PUSH_DATA_DISK_SPACE_FULL
 and FILE_COMMITTED. Without this differentiation, the PartitionLocationMonitor might incorrectly increase the parallelism level for partitions that are already committed or located on workers that are shutting down. 
Alternatively, HARD_SPLIT response can be extended to include the file length, which should be much easier to handle for the compatible issues.
Further Optimization
As a future enhancement, worker can monitor the inbound write speeds for assigned PartitionLocations. If a worker detects that it is overloaded by some high-traffic partitions, it could directly send a SOFT_SPLIT_OVERLOAD [k][l][m][n]responses to ShuffleClient, asking PartitionLocationMonitor to increase the write parallelism for the affected partition and distribute the load more evenly across other workers. We view this approach as a complement to the current design, with plans to implement it in future iterations.
